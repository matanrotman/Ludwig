# RTL/LTR Support

## Goal
Better right-to-left and left-to-right writing and display support — both inside document content, and in the surrounding app UI (sidebar, toolbar) so the whole app feels natural in RTL languages like Hebrew or Arabic, not just the text you type.

## Current state
- The editor already has partial RTL handling — a per-block text-direction attribute and a few targeted line-break fixes — but full bidirectional support has been a known, long-requested gap since 2021 (AppFlowy issue #39: https://github.com/AppFlowy-IO/AppFlowy/issues/39). Mixed-direction content is the weakest part.
- The app's surrounding chrome (sidebar, toolbar, panels) has **no RTL awareness at all** today. The sidebar is pinned to the left edge using hardcoded pixel positioning (`Positioned(left: ...)` in `desktop_home_screen.dart`), not a direction-flexible layout — so nothing in the app chrome currently follows interface language automatically.

## Desired behavior

### Phase 1 — App chrome direction (sidebar + adjacent UI)
- A layout-direction setting that controls where the sidebar docks (left or right).
- **Auto-follow interface language by default**: switching the app's interface language to Hebrew/Arabic auto-flips the sidebar to the right; switching back to English (or another LTR language) flips it back to the left. A manual override is available in Settings for anyone who wants to pin a side regardless of language.
- Collapse/expand icon flips to match — points toward the sidebar's current edge, not hardcoded left.
- Resize drag-handle logic is corrected so dragging toward the sidebar always widens it, regardless of which side it's docked on.
- Adjacent chrome sweep: toolbar/breadcrumb layout and any icons that visually imply "sidebar is on the left" (arrows, hover-reveal edge trigger) are checked and corrected as part of this phase, not left for later.

### Phase 2 — Document content
- **Per-block direction: auto-detect, like Google Docs/Word.** A block's direction follows the first strong-direction character typed into it — no manual per-block toggle needed. (Resolved open question — see "To confirm with me" below.)
- **Mixed-direction lines: standard Unicode bidi.** A line's base direction follows the block (per above), but embedded runs of the other direction (an English word or a number inside a Hebrew sentence) stay in their own direction in place, matching standard browser/Word bidi behavior — not whole-line-only direction. (Resolved open question.)
- **Block-insert ("+") menu opens the wrong side in RTL.** The hover controls next to each block (drag handle, "+" to add below, ⌥-click to add above) are fine, but the block-insert menu that the "+" opens always expands to the right, even when the block/document is RTL — it should open toward the natural reading direction, mirroring how sidebar popovers were fixed in Phase 1 (`sidebarPopoverDirection`/`documentPopoverDirection` helpers already exist as precedent).
- Correct cursor movement, text selection, and toolbar placement inside RTL blocks. **Partially resolved as of 2026-07-14 (two rounds this date)** — the icon-margin gap (30px) is done and user-confirmed live. The floating toolbar had a *second*, deeper root cause found and fixed in round 2 (a debounce race, not the round-1 timing bug alone) — code fix has real confidence, but the test built for it doesn't fail against the pre-fix code, so it genuinely needs a live re-check, not just a glance. The empty-RTL-line cursor bug had two fix attempts in round 2, both reverted after breaking a different scenario than the one each was built for — still open. The multi-run mid-character cursor bug is unchanged, still genuinely open. See "Known related bugs" below.

### Related, but tracked separately
- **RTL table support** has its own spec: `specs/tables.md`. Its first phase (auto-aligning a table pasted from an RTL source) depends on nothing in this phase and can be built independently.
- **Drag-select icon margin** (the drag-handle/"+" icons sit close enough to the first word of a block to interfere with clicking it): not RTL-specific, applies in LTR too. **Bumped to 30px on 2026-07-14, user confirmed live it looks right. Done.**
- **Drag-selecting from a paragraph into/out of a table**: general selection-handling gap, not RTL-specific. Logged for a future session, not scoped into this spec or into `tables.md`.
- **Block-insert "+" on a non-empty block creates a new block below rather than opening the menu in place**: investigated 2026-07-15, turned out to be existing, by-design editor behavior (Notion-style "+"), not a bug — not in scope for this spec.
- **A block created via Enter-split from an RTL sibling stays RTL even when pure English is then typed into it**: flagged 2026-07-14, not actively re-verified this session since it wasn't one of the items asked for — but the direction-lookup fix from 2026-07-15 (`text_direction_mixin.dart` no longer depending on a mounted render state) very likely already fixes this as a side effect, and existing fork tests for "auto empty text don't use previous node direction because we can determine by the node text" already cover the same underlying logic. Worth a quick confirmation next time this comes up, not urgent.

### Known related bugs, not yet scoped
Status as of 2026-07-14, after two fix rounds the same date (see Session Log for full detail):
- **Cursor renders mid-character/mid-token in real (multi-run) mixed Hebrew/English text — still genuinely open, unchanged in round 2.** The "mid-token inside a date" claim is confirmed and has a passing regression test; a narrower, distinct anomaly (the caret jumping to the wrong side right after a trailing comma exits an embedded run) is confirmed but deliberately left un-fixed via a `skip`ped test — a fix attempt (per-character `getBoxesForSelection` lookup) produced byte-identical output to the existing approach, so the issue sits inside Flutter's own bidi run classification, not this wrapper. Needs a reference implementation to compare against or a live look to define "correct." `appflowy_rich_text.dart` (fork), `getCursorRectInPosition`; `caret_bidi_test.dart`.
- **Cursor far from the actual typing position on a fresh empty RTL line ("creating a new line has a very far cursor") — still genuinely open, two fix attempts reverted in round 2.** Root cause confirmed with high confidence: the correction's `contentWidth ?? ... ?? 0` chain never falls through (0.0 isn't null, `_renderParagraph.size.width` is always 0.0 for empty text), so it's been a permanent no-op. Fixing it properly is harder than that diagnosis suggests: a `LayoutBuilder`-captured max-width fixed plain paragraphs but overshot ~600px for headings (different internal layout — `Row`+`Flexible`+`MainAxisSize.min` vs. a full-width `Column`); deriving the true right edge from the widget's own outer `RenderBox` gave a *consistent* edge across both block types but then broke the pre-existing "caret near a just-typed character" tests, since a real typed RTL character's position didn't clearly match "the right edge" either in this test environment. Both attempts reverted rather than ship something unstable. Full findings in `appflowy_rich_text.dart`; next attempt should start with a live repro (press Enter, look), not another headless guess.
- **Floating selection toolbar — a second, deeper bug found and fixed in round 2; genuinely needs live re-confirmation, not just a glance.** Round 1's fix (deferring `DesktopFloatingToolbar.initState()`'s geometry read to post-frame) was real but only addressed one of two bugs — the user re-tested live and the toolbar was still landing at the selection's start. Round 2 read the actual drag-gesture code directly and found `Selection.end` genuinely tracks live drag position correctly (so anchoring on the selection's extent was always the right target) — the real bug was a **debounce race in the outer `FloatingToolbar` wrapper** (pre-existing upstream file): scroll-offset changes (firing every frame during auto-scroll) and selection changes shared one debounce key, so a synchronous `Duration.zero` scroll tick could cancel a pending, more-authoritative 200ms selection-driven show. Fixed by splitting the keys and deferring the scroll-triggered show to post-frame too. The new test drives the real `FloatingToolbar` → `DesktopFloatingToolbar` wiring but honestly does not fail against the pre-fix code (a single `jumpTo()` doesn't recreate a real drag's continuous scroll-tick stream) — confidence rests on the code reasoning, not a proven failing-first test. `floating_toolbar.dart` (fork, pre-existing upstream file — flag as upstream-worthy); `floating_toolbar_debounce_race_test.dart`.
- **Icon-margin gap — bumped to 30px, user confirmed live 2026-07-14. Done.** `editor_configuration.dart`.
- **Arrow-key navigation reverses direction at a language boundary in a bidi line — root cause pinned down 2026-07-16, fix scoped but NOT built.** In a sentence that mixes Hebrew and English (the everyday case: a Hebrew sentence containing an English phrase or a date), holding the left arrow moves the caret leftward through the Hebrew, then **reverses and travels rightward** through the embedded English run, then flips back. Makes editing the end of an embedded phrase genuinely hard. **This is a design limitation, not an incidental bug — the user's report is a faithful description of what the code does.** Two facts establish that:
  1. **Movement is logical (offset arithmetic), never visual.** `position_extension.dart:39-44` and the identical logic in `selection_commands.dart:276-288` move the caret with `delta.prevRunePosition(offset)` / `nextRunePosition(offset)` — plain rune-index arithmetic on the Delta string. No `TextPainter`, no layout consulted. **`getOffsetBefore`/`getOffsetAfter` (Flutter's visual bidi traversal) return zero hits across the entire fork `lib/`** — it is never used.
  2. **Direction is resolved once per BLOCK, not per run.** `arrow_left_command.dart:223-229` — `isRTL(editorState)` reads `node?.selectable?.textDirection()` for the whole block. So in a Hebrew paragraph, left-arrow maps to logical *increment* for the entire line; through Hebrew that renders leftward (correct), but inside an embedded English run the same logical step renders **rightward**. Same flip in `arrow_right_command.dart` and in the word/select variants (`arrow_left_command.dart:89, 142, 176, 210`).
  **Decided behavior (user, 2026-07-16): visual movement — the left arrow always moves the caret visually left, never reverses.** This matches macOS and Windows native text fields, so it matches the rest of the user's machine.
  **Honest cost — scope this as its own session, do not bolt it onto another:** this is a *semantic rewrite* of caret movement (logical → visual traversal via the laid-out `TextPainter`), not a tweak. It changes arrow-key behavior for **all** text, not only bidi text, so it needs a deliberate regression pass over plain LTR editing too. It lands in the editor fork and diverges us further from upstream — which cuts against the fork-maintenance goal, so weigh whether it's upstream-worthy (it plausibly is: it's a correctness gap in the editor's own bidi story, not a fork-specific need). Note this is *distinct* from the caret-**rendering** bugs above: those are about where the caret is drawn; this is about where it moves to. `caret_bidi_test.dart` covers rendering only and explicitly "never arrow-key movement" — a new test file is needed.

## Editor fork — upstream merge (deferred 2026-07-15; read this before attempting it)

The fork-sync check reports the editor fork as **36 behind / 10 ahead** of
`AppFlowy-IO/appflowy-editor`. That number is real but misleading, and it has already
prompted one merge attempt that was called off. Read this before it prompts another.

**Why "36 behind" is the wrong target.** `AppFlowy-IO/AppFlowy` pins `appflowy_editor` at
`470c4e7` — *byte-identical to our merge base* (`git merge-base` and `git rev-parse 470c4e7`
both give `470c4e77c71b63f693ce0923a927afcd667d6f3b`). The app never followed the editor
package. Measured against the upstream that actually matters, we are **0 behind**. The 36
commits belong to a package our app doesn't track.

**It isn't an editor merge, it's a Flutter migration.** 35 of the 36 commits sit at or after
`49a2b1c0`, which raises the editor's floor to Flutter ≥3.32.0 (upstream CI now runs 3.38.5).
The app, AppFlowy-IO's CI, and this machine are all on 3.27.4, and the editor's pubspec would
demand `flutter: ">=3.32.0"` — so `pub get` fails before anything compiles. Merging means
dragging all of AppFlowy (404 files import the editor; 12 reach into private `src/`;
`editor_i18n.dart` carries 111 overrides; 52 block-component subclass sites) onto a Flutter
version its own upstream doesn't use, producing an AppFlowy 0.11.4 + editor 6.1.0 combination
nobody has tested. The single pre-bump commit is an offline-collab example app — no value.

**The trigger to revisit:** when AppFlowy-IO bumps its own `appflowy_editor` pin past
`470c4e7`. Then we follow them, on their Flutter version, with their testing behind us.

**Landmines to expect when it does happen** (each cost real investigation):
- **`floating_toolbar.dart` — merges clean, does not compile.** Upstream `b1e78536` added
  `Debounce.cancel(_debounceKey)` to `dispose()`; our branch *deleted* `_debounceKey`, splitting
  it into `_selectionDebounceKey`/`_scrollDebounceKey`. Different lines, so git won't flag it —
  the result is a dangling symbol. Cancel both keys there, and keep upstream's adjacent
  `_toolbarContainer?.dispose()` (they inlined `_clear()` deliberately; don't revert it).
  *May be moot:* if our upstream PR is accepted, this fix leaves the fork entirely.
- **`appflowy_rich_text.dart` (~line 455) — the only real textual conflict, and it's convergent.**
  Upstream `1c2d58b6` independently fixed the same placeholder bug we did, replacing
  `updateTextStyle(Colors.transparent)` with an empty span and flattening
  `getPlaceholderTextSpan()`. Take upstream's `textSpan.copyWith(text: '')`, keep our comment,
  retire our version. (`copyWith` preserves `children` where ours dropped them — equivalent here,
  since upstream's span is now flat and all three app call sites only use `updateTextStyle`.)
- **`f882d958` (awesome_lints) is pure noise on our files** — it touches 10 of our 12, inserting
  only blank lines. Expect fat conflicts carrying zero semantics.
- **Our three `docs:` commits add no doc files.** They are comment blocks inside
  `appflowy_rich_text.dart`. A merge tool will drop them silently — re-check them by hand.
